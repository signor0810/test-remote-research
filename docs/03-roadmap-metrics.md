# 導入路線與成效衡量

## 導入原則

> **習慣先行，程式碼後補。**
> 每個 Phase 都必須在**下一個 Phase 開始前**就已經產生可感知的價值。
> 若 Phase 0 一週後你覺得沒差，就停手 —— 那代表問題不在資料彙整，繼續蓋系統只會浪費時間。

---

## Phase 0 · 純習慣（第 1 週，零程式碼）

**做什麼**：只執行習慣 H1–H4（Jira key、一任務一 session、收尾三行、friction 記錄）。
週五手動把三個工具的摘要複製到週報模板裡。

**驗收**：週報產出時間從 <目前> 降到 30 分鐘以內；`friction.md` 累積 ≥ 10 筆。

**這個 Phase 的真正目的**是驗證「原料是否足夠」。如果手動拼裝時發現資料根本不夠寫週報，那自動化也救不了 —— 要先修習慣。

---

## Phase 1 · 事件庫 + 週報草稿（第 2–4 週）

**做什麼**：
1. herdr adapter：把三個工具的 session / 摘要匯出成原始 JSON。
2. Normalizer：轉成 `WorkEvent`，解析 Jira key，標記 sensitivity，寫入 `events/YYYY-Www.jsonl`。
3. 週報合成器：週五 16:00 跑，輸出 Markdown 草稿。
4. 先**手動貼**到 Confluence（連接器留到 Phase 2）。

**先決定的事**：L2–L4 執行環境必須落在內部邊界內（見架構文件 §2c）。這件事晚決定，之後要重寫資料流。

**驗收**：週報審稿時間 ≤ 15 分鐘；事件覆蓋率 ≥ 80%。

**降級行為**：合成器掛掉時，直接輸出原始事件清單，不阻塞你交週報。這條規則從第一天就要有。

---

## Phase 2 · 雙向連接器（第 5–8 週）

**做什麼**：Jira / Confluence 連接器（讀 issue、寫週報頁）、Outlook 連接器（讀每週更新、產草稿信）、Jira comment 回寫（預設關閉，觀察一個月再開）。

**驗收**：週五完全不需要手動複製貼上；審稿時間 ≤ 10 分鐘。

---

## Phase 3 · 回顧與機會分析（第 9 週起，每月）

**做什麼**：月度分析器讀 friction + 工具用量 + 週報 diff，輸出自動化機會排行榜。

排序公式：

```
價值分數 = (月發生次數 × 每次分鐘數 × 12) / 預估建置人日
```

**驗收**：每月產出至少 3 個候選項；實際動手 1 項並在下一個月度回顧中量到時間下降。

---

## 成效指標

| 指標 | 定義 | 目標 | 何時看 |
|---|---|---|---|
| **週報產出時間** | 從草稿產生到寄出 | ≤ 10 min | 每週 |
| **草稿採用率** | 未被你編輯的段落比例 | ≥ 70% | 每週 |
| **事件覆蓋率** | 有 Jira key 的事件 / 總事件 | ≥ 90% | 每週 |
| **unassigned 段落長度** | 週報中「其他」段的項目數 | ≤ 2 | 每週（H1 的健康度） |
| **hermes 額度使用率** | 月用量 / 200 | 60–90% | 每週 |
| **friction 收斂** | Top 1 friction 的月累計分鐘數 | 逐月下降 | 每月 |
| **承諾達成率** | 上週計畫中本週完成的比例 | 觀察即可，不設目標 | 每月 |

> 「草稿採用率」是整個系統最重要的單一指標。它低於 50%，代表 L4 的 prompt 沒對齊你的寫法 —— 修 prompt，不要自己補寫。

---

## 失敗訊號（出現就該停下來檢討）

- 你開始**繞過**系統，直接手寫週報 → 草稿品質不合格，回頭修 L4。
- `friction.md` 連續兩週是空的 → 不是沒有摩擦，是記錄成本太高，簡化格式。
- unassigned 段落持續肥大 → H1 沒落實，任何自動化都補不回來。
- 為了維護採集腳本花掉的時間 > 它省下的時間 → 該項自動化應直接砍掉。
